  2. ALMACENAMIENTO PERSISTENTE (AUDIT STORAGE / ZIPs)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CONTEXTO: El sistema guarda un ZIP comprimido de cada archivo cargado
en audit_storage/{catalog_id}/{fecha}/{timestamp_usuario_archivo.zip}.
Esto sirve para auditoría y reproceso. Si se guarda DENTRO del contenedor
Docker y el contenedor se reinicia o redeploya, los archivos se pierden.
Hay que definir la estrategia de persistencia antes de producción.

2.1  ¿El banco tiene almacenamiento de red (NAS/SAN/NFS) disponible
     para montar en el servidor donde correrá Docker?
     - Si sí: se monta esa carpeta de red como bind mount al contenedor.
     - Si no: los ZIPs quedan en el disco del servidor mismo.

2.2  ¿Quién del equipo del banco puede acceder a esos ZIPs para
     revisarlos manualmente si hay un reclamo o auditoría?
     ¿Necesitan acceso por interfaz web, o es suficiente acceso al servidor?

2.3  ¿Cuánto volumen de archivos se estima por mes?
     (Número de catálogos × frecuencia de carga × tamaño promedio del archivo)
     Esto define cuánto espacio en disco reservar.

2.4  ¿Los ZIPs tienen política de retención definida?
     ¿Cuánto tiempo deben guardarse antes de poder eliminarse?
     (6 meses, 1 año, indefinido por regulación)

2.5  ¿Los ZIPs necesitan backup automático?
     ¿El banco tiene solución de backup centralizada donde incluirlos?

2.6  ¿Se necesita alguna funcionalidad para descargar un ZIP desde
     el portal web (panel de historial), o es suficiente con ver el log?

2.7  ¿El campo ruta_zip_auditoria en el log debe ser una ruta del servidor
     o una URL descargable desde el portal?

  7. ESTRATEGIAS DE CARGA (overwrite / append / reproceso)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CONTEXTO:
  overwrite  → borra toda la tabla y la reemplaza con el archivo nuevo.
               Usar para catálogos estáticos o de referencia completa.
  append     → agrega filas nuevas sin tocar lo que ya existe.
               Riesgo: si subes el mismo archivo dos veces, se duplican.
  reproceso  → borra solo las filas de las fechas que trae el archivo
               y las reinserta. Ideal para snapshots diarios corregibles.

7.1  ¿Cómo llegan los archivos de snapshot diario — el archivo de hoy
     trae solo las filas de hoy, o trae todo el histórico acumulado?

7.2  ¿Qué columna identifica la fecha del snapshot en cada catálogo?
     Hoy el sistema busca: fecha_proceso, fecha, fecha_carga, date.
     Si el banco usa otro nombre, hay que agregarlo.

7.3  ¿Hay catálogos que se cargan más de una vez al día?
     ¿Puede el mismo archivo subirse por error dos veces?
     (Esto define si append es seguro o si necesita protección contra duplicados)

7.4  ¿Existe algún caso donde necesiten reemplazar filas por un campo
     distinto a fecha — por sucursal, por producto, por código?
     (Hoy reproceso solo funciona por fecha)

7.5  ¿Las tablas destino ya tienen datos históricos antes del primer uso
     del portal? Si es así, un overwrite inicial los borraría — ¿eso está
     contemplado o hay que hacer una carga inicial especial?

7.6  ¿Qué pasa si un publicador sube un archivo incorrecto y ya se escribió
     en la BD? ¿Hay proceso de rollback o se corrige subiendo otro archivo
     con reproceso?

7.7  Para los catálogos de tipo snapshot diario, ¿la tabla destino acumula
     todos los días (particionada por fecha), o solo guarda el último día?

  NOTAS ADICIONALES
============================================================

- La variable LDAP_REQUIRED_GROUP en .env está lista pero vacía.
  Debe llenarse antes de producción con el grupo AD exacto.

- El campo audit_storage necesita estrategia de persistencia
  antes de dockerizar (bind mount, Docker volume, o NAS).

- Las migraciones SQL (db/migrations/) deben ejecutarse en el
  SingleStore de producción antes del primer despliegue.

- docker-compose.prod.yml está mencionado en el .env pero no existe
  aún en el repositorio — hay que crearlo antes del despliegue.

- La columna de fecha para estrategia "reproceso" busca por defecto:
  fecha_proceso, fecha, fecha_carga, date.
  Si los catálogos del banco usan otro nombre hay que agregarlo al código.
