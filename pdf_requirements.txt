Data Gatekeeper
Documento de Arquitectura: Portal de Ingesta y Validación de Catálogos (Data Gatekeeper)
1. Objetivo del Sistema
Desarrollar una aplicación web interna que descentralice la carga de catálogos manuales (CSV, TXT, Excel, etc.), transfiriendo la responsabilidad de la calidad
del dato al usuario final. El sistema validará estructuras y reglas de negocio en memoria antes de impactar directamente la base de datos, eliminando
procesos batch intermedios y asegurando la integridad transaccional.
2. Componentes de la Arquitectura

Funcionalidades Clave:

Tecnología Sugerida: Streamlit (para una arquitectura unificada Front/Back rápida) o FastAPI (si se requiere separar el backend para devolver un JSON
de errores).
Autenticación: Librería ldap3 para conectar con el Active Directory / Kerberos LDAP de la empresa.
Motor de Procesamiento: pandas para lectura del archivo en memoria RAM, no creo que sea necesario usar spark para cosas sencillas.
Motor de Validación: pandera para definir esquemas estrictos (Data QA) de forma declarativa.
Base de Datos Principal: SingleStore.
Esquema App: Para metadatos del sistema (usuarios, permisos, configuración de catálogos).
Base de Datos: Hive y Singlestore
Esquema Data: Las tablas finales de negocio donde aterrizan los catálogos, deben encontrase en los metadtos de singlestore.
Almacenamiento Físico (Cold Storage): Un volumen de Docker montado (bind mount) en el servidor para almacenar de forma inmutable una copia
comprimida del archivo original subido, exclusivamente para fines de auditoría.
Validación Estructural: Que el archivo contenga exactamente las columnas esperadas (ej. cod_rol, rol, estado, peso_1). Ni una más, ni una
menos.
Validación de Tipos (Casteo Seguro): Comprobar que columnas numéricas (int, float) no contengan caracteres alfanuméricos ocultos o nulos no
permitidos.
Validación de Dominio: Reglas de negocio específicas (ej. el campo estado debe ser estrictamente 0 o 1; peso_1 debe ser un número entero).
Manejo de Errores: Si la validación falla, el proceso se aborta inmediatamente, no se guarda nada, y se devuelve un JSON al Frontend con la lista exacta
de errores para que el usuario los corrija en origen.
SingleStore: Se utilizarán bloques de transacciones SQL (BEGIN ... COMMIT) para asegurar atomicidad.
Hive: Se basará en el manejo de particiones dinámicas/estáticas para asegurar reemplazos limpios sin afectar datos históricos.
